> **Catch-up theme:** The character became a hierarchy, objects became genuinely usable, navigation behaviour was tightened up, and NPCs finally learned to shoot.

## 1. Character Hierarchy Continued

The character model continued evolving from the original block structure into a proper hierarchical rig.

- Arms were split into upper-arm and lower-arm sections joined around the elbow.
- Lower-arm groups were introduced to establish the transform hierarchy required for more expressive held-object animation.
- The next logical level is `HandGroup`, beneath the lower arm.

Intended hierarchy:

```text
UpperArmGroup
    └── LowerArmGroup
          └── HandGroup
                ├── Hand
                └── AttachmentPoint
                      └── Attached Object
```

Movement should propagate naturally from upper arm → lower arm → hand → attachment point → held object.

---

## 2. Walking Animation — Bounce

A subtle vertical bounce was added to the NPC walking animation using the existing walking cycle.

The first version is deliberately subtle and gives the low-poly NPC more physical weight without requiring additional geometry or a complex animation system.

---

## 3. Visibility-Based Character Updates

Changing character options initially caused the NPC to be rebuilt, producing a brief black flash.

This was changed so that:

- The complete NPC model is only replaced when the base NPC model itself changes.
- Other character options toggle visibility of existing meshes.
- Existing hierarchy and animation are preserved.
- Unnecessary scene teardown/recreation is avoided.

This removed the redraw/black-flash problem and established a cleaner lifecycle distinction between replacing a character and changing what is visible.

---

## 4. Attachment System Became Operational

The independent-object architecture moved from an architectural experiment into practical use.

Current pieces include:

- `AttachmentPoint`
- `AttachmentSystem`
- Independent object classes
- NPC awareness of its carried object
- `setObject()`
- `useObject()`
- `dropObject()`

The NPC can now know which object it is carrying and interact with it through the object system.

The key principle remains:

> The object knows how it can be attached and used; the character does not need to know the internal details of every object.

---

## 5. Object Lifecycle — Use and Drop

The object lifecycle was extended beyond simply attaching an object.

```text
Create
  ↓
Attach
  ↓
Use
  ↓
Detach
  ↓
Fall / interact with environment
  ↓
Reattach
```

`dropObject()` currently removes the object from the scene as a temporary V1 implementation.

A `GravitySystem` placeholder exists. The intended next version is for a detached object to remain in the world and fall under gravity rather than disappear.

---

## 6. Object Use Model

Different objects can now be treated as independently usable:

```text
SMG
  └── Use() → Shoot

Clipboard
  └── Use() → Read

Clipboard + Pen
  └── Use() → Write
```

The player and NPC are intended to use the same object interaction mechanism.

The character decides **when** to use an object; the object owns the details of **how** it is used.

---

## 7. Navigation Rotation Fix

The earlier 90° / 270° NPC turning issue was resolved.

NPCs now rotate toward their target using the shortest turn rather than taking the visually incorrect long route.

Investigation also showed that Three.js Y rotation values do not necessarily correspond to intuitive compass-style angles. The useful distinction is between conceptual heading, world direction and Three.js's local rotation representation.

The visual behaviour is now correct.

---

## 8. NPC Pursuit Refinement

Normal NPC movement continues to use controlled turning.

A future refinement is to make pursuit rotation substantially faster than normal movement rotation, giving an NPC that has spotted the player a greater sense of urgency without making rotation instantaneous.

---

## 9. NPC Aggression V1 — First Enemy Shot

A major gameplay milestone was reached:

> **NPCs can now shoot at the player.**

The first implementation deliberately skipped the line-of-sight raycast and hooked shooting into existing player detection.

```text
NPC sees Player
      ↓
NPC.useObject()
      ↓
SMG.use()
      ↓
BulletSystem
      ↓
Bullet travels toward Player
```

The first rough demo confirmed that the bullet physically travels from the NPC's weapon toward the player.

### First-fire bug

The first implementation spawned the bullet too close to the NPC, causing the NPC to immediately collide with its own projectile and die.

A small Z-position adjustment corrected the projectile spawn position.

---

## 10. Bullet Creation Refactor

Bullet creation was moved into `BulletSystem`.

The SMG now requests a shot rather than owning the projectile lifecycle:

```text
SMG
  ↓
"I want to fire"
  ↓
BulletSystem
  ↓
Creates and manages bullet
```

This keeps weapon behaviour separate from projectile management.

---

## 11. Friendly Fire Discovery

With approximately 50 NPCs active, NPC shooting immediately revealed another V1 limitation: NPCs were shooting and killing each other.

For initial testing, collision-system death behaviour was temporarily disabled so the end-to-end firing system could be observed.

The next refinement is to add a team/faction indicator to bullets so collision handling can distinguish friendly from hostile targets.

```text
NPC bullet → NPC target
    same team → ignore

NPC bullet → Player
    different team → hit
```

This can later grow into a more general ownership/faction concept.

---

## 12. NPC → Player Firing Vector

The firing system is being refined to calculate the vector directly between the SMG firing position and the player target position.

```text
SMG
 ├── muzzle position
 └── target position
          ↓
     direction vector
          ↓
    BulletSystem
```

This keeps the weapon responsible for determining how it fires while leaving projectile creation and lifecycle to `BulletSystem`.

The same mechanism can eventually be shared by NPC and Player weapons.

---

## 13. Muzzle Flash

A small `Blast()` mesh is now being used as a muzzle-flash representation.

The muzzle flash appears successfully, but its exact positioning still needs visual refinement.

The intended review method is a stationary NPC first, allowing the weapon, muzzle, flash and hand positions to be tuned without movement complicating the result.

A dedicated shooting animation has not yet been added.

---

## 14. Shooting Animation

The NPC state system needs to communicate shooting behaviour to the animation handler.

The intended relationship is:

```text
NPC State
    ↓
Animation Handler
    ↓
SHOOT animation
```

The animation adjustment is understood conceptually but is not yet fully applied.

The current muzzle flash and projectile behaviour therefore provide the gameplay proof before the visual shooting animation is completed.

---

## 15. Line of Sight — Next Behaviour Layer

The existing vision system establishes that the NPC can detect the player.

The next refinement is a raycast between NPC and player during the aggressive state:

```text
Vision detects Player
        ↓
CHASE / aggressive state
        ↓
Line-of-sight raycast
        ↓
Clear?
   ↙       ↘
 YES        NO
 ↓           ↓
UseObject   Continue pursuit
 ↓
SMG.use()
```

This distinguishes "I know where the player is" from "I have a clear line of sight to the player."

---

## 16. SoundSystem — Upcoming

After NPC firing is functioning cleanly, the next major supporting system is expected to be `SoundSystem()`.

The first obvious use will be the SMG firing sound.

```text
SMG.use()
   ├── BulletSystem → projectile
   ├── Muzzle flash
   └── SoundSystem → firing sound
```

Sound can later become another gameplay signal for footsteps, impacts, alarms and NPC investigation.

## 17. Development / Debug Pages

The project continues to expose internal engine behaviour through standalone HTML development pages.

The Character Designer and waypoint/pathfinding visualisation page follow the same philosophy:

> Make the engine's internal behaviour visible rather than relying only on the main game to reveal problems.

This approach has already helped expose rotation and pathfinding assumptions.

## 19. Future In-Game Video

A future storytelling capability was identified using Three.js video textures.

An MP4 can eventually be used as a video texture on an in-game screen.

The existing object/use architecture provides a natural route:

```text
Player
  ↓
useObject()
  ↓
Monitor / Computer
  ↓
PlayVideo()
  ↓
VideoTexture
```

Potential uses include security monitors, computer terminals, briefings, emergency broadcasts, surveillance footage and environmental storytelling.

This remains a future production-value feature rather than current Game One scope.

---

## 20. Development Philosophy

The project continues to follow:

> **V1 is the point at which an idea becomes real. V2 happens when reality gives us a reason.**

Recent examples:

- First working attachment before multi-attachment.
- First working object use before elaborate object-state systems.
- First NPC shot before line-of-sight refinement.
- First muzzle flash before shooting-animation polish.
- First bullet team flag before a complete faction system.
- First gravity placeholder before multi-level surface resolution.

This continues to produce reusable engine capabilities without requiring the entire future architecture to be designed in advance.
