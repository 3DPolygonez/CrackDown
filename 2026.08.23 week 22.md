## 1. Character Designer

The Character Designer continued to evolve from a simple mesh preview
into a genuine development laboratory.

-   Dynamic character mesh selection is working.
-   Character parameters can be overridden from outside the character
    definitions.
-   Existing defaults remain useful while specific definitions such as
    the Scientist can override them.
-   Front-end controls now propagate down through the character
    definition layer.
-   Speed can be adjusted through the designer.
-   Include/exclude controls are available for character elements.
-   Character definition JSON is displayed directly in the designer.
-   Touch-screen swipe controls were added for camera rotation and zoom.
-   The background was changed to light green so character shadows
    remain visible.
-   A Blank character mesh was added as a neutral/orange NPC.
-   The designer was tested on a phone and its Open Graph preview was
    tested.
-   LocalStorage was identified as the future mechanism for saving and
    retrieving named character definitions without a backend.

**Core principle:** the designer should make experimentation faster than
editing values manually in code.

## 2. Character Construction

Hands were added to the character model and exposed through the
Character Designer.

The arms were then redesigned as two sections joined around the elbow.
The first version deliberately has no additional elbow/forearm animation
yet.

This creates the structural hierarchy needed for future elbow movement,
forearm rotation, held-object posing, two-handed weapon poses and more
sophisticated animation.

## 3. Independent Objects

A major architectural milestone was reached:

> **Objects are no longer permanently part of the NPC mesh.**

The SMG was removed from the Scientist/NPC default mesh and replaced
with an independently represented object.

Initial object classes were created for:

-   Pen
-   Clipboard
-   SMG

The Character Designer can select which object is associated with the
character.

The main game was also updated to give NPCs randomly selected objects,
proving that the object/attachment architecture works outside the
Character Designer.

## 4. AttachmentPoint

The first version of the attachment architecture was implemented.

The initial concept was deliberately simple:

> **An AttachmentPoint is a coordinate/location that identifies where
> something can connect.**

The first NPC implementation contains an attachment point on the hand.
Objects can also expose their own attachment point.

The immediate goal was:

### Two Points Meet.

That goal was achieved.

The object is positioned using the relationship between the two
attachment points, without requiring the hand code itself to know what
object it is holding.

``` text
Character Hand
      ↓
AttachmentPoint
      ↓
AttachmentSystem
      ↓
Object AttachmentPoint
      ↓
Object
```

The first working object was the clipboard.

## 5. AttachmentSystem

An `AttachmentSystem` class was created and brought into the first
working attachment implementation.

Its intended responsibility is deliberately broader than any particular
object or character:

> **The AttachmentSystem should be capable of connecting any two
> compatible things through their AttachmentPoints.**

Potential future relationships include:

-   NPC → hand-held object
-   NPC → object on back
-   Weapon → weapon rack
-   Character → vehicle seat
-   Chief Scientist → Cyclops seat 🚜

The distinction established this week is:

-   **AttachmentPoint** = where/how an item can connect.
-   **AttachmentSystem** = the mechanism that establishes and manages
    the connection.

## 6. Attachment Agreements and Multi-Attachment

The next architectural step is to describe what objects are actually
allowed to attach to.

For example:

``` text
Weapon
 ├── can be held by NPC
 ├── can attach to NPC back
 └── can attach to weapon rack
```

The next immediate extension is supporting multiple simultaneous
attachments:

``` text
Right Hand → Clipboard
Left Hand  → Pen
```

This will eventually allow combinations such as clipboard alone → read,
clipboard + pen → write, and two-handed weapons.

The existing single-attachment implementation is deliberately being
treated as V1 rather than over-generalised prematurely.

## 7. Object Use()

The longer-term object model is beginning to emerge.

Each object will eventually have a `Use()` capability.

``` text
Gun
 └── Use() → Shoot

Clipboard
 └── Use() → Read

Clipboard + Pen
 └── Use() → Write
```

The key design principle is:

> **An object cannot sensibly be used until the prerequisites for using
> it exist.**

The sequence is therefore:

``` text
Object exists
    ↓
Object can be attached
    ↓
Object is correctly held
    ↓
Object becomes usable
    ↓
Character chooses to use it
```

## 8. Detachment and Gravity

Detachment is the next natural consequence of independent objects.

At present, changing the selected object effectively swaps the
character's held mesh.

The intended future behaviour is:

``` text
Held Object
     ↓
Detach
     ↓
No longer parented to Character
     ↓
GravitySystem
     ↓
Falls
     ↓
Supported by environment
```

A `GravitySystem` class was created in anticipation of this.

For initial testing, ground level can be assumed to be `y = 0`. Later,
gravity should resolve the actual supporting surface beneath an object,
allowing for ground, platforms, roofs, tables, vehicle interiors and
other supporting geometry.

## 9. Waypoint Debug Laboratory

A dedicated HTML page was created for visualising NPC waypoint routes.

This follows the successful pattern established by the Character
Designer:

> **Expose the engine's internal behaviour through a simple visual
> development page.**

Returning to the waypoint system also exposed older assumptions and
inconsistencies that had been hidden by simply watching NPCs move.

## 10. Rotation Issue Identified

An inconsistency was noticed while revisiting waypoint behaviour:

> Some rotations resolve to 90° while equivalent movement can require
> 270°.

This has not yet been patched.

The desired solution is not waypoint-specific exceptions, but a single
canonical representation where direction is translated into rotation
consistently.

The eventual fix should benefit waypoint movement, NPC turning,
animation, camera direction and pathfinding.

## 11. Pathfinding Revisit List

The new visual debugging approach brought several previously discussed
pathfinding improvements back into focus:

-   Eight-direction movement.
-   Diagonal movement costs of approximately 1.4 versus 1.0 for
    orthogonal movement.
-   Better closest-node resolution.
-   Visualisation of nodes and explored paths.
-   Obstacle/corner handling when diagonal movement is enabled.
-   Support for different NPC footprints.
-   Eventually moving toward A\*.

The earlier idea remains particularly interesting:

``` text
40 × 40 map

1 × 1 NPC → 40 × 40 navigation resolution
2 × 2 NPC → 20 × 20 navigation resolution
```

Smaller units could therefore navigate spaces unavailable to larger
units.

## 12. Engine / Architecture Reflection

One of the strongest observations of the week was that the project is
beginning to produce its own reusable engine knowledge.

The first game is teaching what needs to exist:

-   Character definitions
-   Character hierarchy
-   Animation
-   Attachment points
-   Attachment systems
-   Independent objects
-   Waypoints
-   Pathfinding
-   Vision
-   Camera
-   Environment
-   Debug tooling

The longer-term insight is that these components can become a much
stronger starting point for a second game.

> **A game is being built while simultaneously discovering and building
> the tools required to make the next game easier.**
