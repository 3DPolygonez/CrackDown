# Crack Down Remake --- Weekly Development Summary

## Overview

This week marked the beginning of the **Character Laboratory**.

The project moved from manually changing character values in code toward
an interactive character-definition workflow, with a new standalone
`character.html` page, live controls, runtime model switching,
definition display, speed controls, and the first steps toward a
reusable character authoring platform.

At the same time, larger architectural ideas emerged around equipment,
multiple state dimensions, object interaction, navigation profiles
and---much later---the possibility of an AI-assisted character authoring
workflow.

------------------------------------------------------------------------

## 🥼 Character Designer --- Version 1 Begins

Created a standalone `character.html` page specifically for character
development.

The page starts a deliberately minimal environment:

-   One NPC.
-   No environmental objects.
-   Camera automatically focused on the NPC.
-   Zoom configured for character inspection.
-   Character-specific controls available independently of the main
    game.

This replaces the old loop of:

``` text
Change code → Reload game → Find NPC → Adjust camera → Inspect
```

with:

``` text
Change value → Immediate visual feedback
```

This is the beginning of the **Character Laboratory**.

------------------------------------------------------------------------

## ⚙️ Runtime Character Definition Overrides

The existing `CharacterDefinition` architecture proved particularly
useful.

New front-end controls now pass user changes all the way down into the
character-definition layer.

The configuration hierarchy is becoming:

``` text
Base Character Defaults
        ↓
Character-specific Defaults
        ↓
Designer / User Overrides
        ↓
Final Character Definition
```

The Scientist can retain her own default proportions while the designer
overrides any known parameter without modifying the Scientist definition
itself.

A speed control was also added.

------------------------------------------------------------------------

## 🔄 Runtime Base Mesh Switching

The Character Designer can now change the base character model through
the UI.

The first implementation exposed a useful bug: the new model appeared,
but animation stopped.

The cause was wonderfully mundane:

> The old mesh group had not been removed from the scene before the new
> one was added. 😹

After correcting the lifecycle, the first live character/model switching
control worked successfully.

This establishes the designer loop:

``` text
UI
 ↓
Character configuration
 ↓
Old representation removed
 ↓
New representation created
 ↓
Scene updated
 ↓
Immediate visual result
```

## 🧹 Dynamic Entity / Resource Lifecycle

Runtime model replacement prompted the first serious consideration of
Three.js resource management.

Important lifecycle concepts identified:

-   Remove old groups from the scene.
-   Release references to obsolete objects.
-   Consider animation references and callbacks.
-   Dispose of geometry owned exclusively by the character.
-   Dispose of materials owned exclusively by the character.
-   Dispose of unique textures when appropriate.
-   Avoid disposing shared assets still used by other entities.

A future `Character.dispose()` boundary was identified as a useful
architectural direction.

The distinction between `scene.remove()`, `dispose()`, and JavaScript
garbage collection was clarified.

No large resource-management framework is being introduced yet; the
intention is to let the Character Designer expose the real requirements
first.

## 📋 Equipment & Object State Architecture

The discussion around characters carrying objects led to a useful
architectural distinction.

The existing FSM answers:

> **What is the character doing?**

For example:

``` text
IDLE
PATROL
CHASE
SEARCH
RETURN
```

Equipment answers:

> **What is the character carrying or using?**

And an object may eventually have its own state:

``` text
PISTOL
  ↓
DRAWING
  ↓
READY
  ↓
FIRING
  ↓
COOLDOWN
```

The preferred direction is therefore to avoid a giant combined FSM such
as:

``` text
CHASE_WITH_PISTOL
CHASE_WITH_PISTOL_AIMING
CHASE_WITH_PISTOL_FIRING
CHASE_WITH_SMG
...
```

Instead, independent state dimensions can eventually combine:

``` text
Character State = CHASE
Equipment       = PISTOL
Object State    = AIMING
```

This avoids combinatorial explosion while allowing richer behaviour.

## 🤖 Long-Term AI-Assisted Character Authoring

A major conceptual development was the possibility of eventually turning
the Character Designer into an **AI-assisted authoring platform**.

The proposed workflow is:

``` text
Human
  ↓
Natural language intent
  ↓
AI Agent
  ↓
Controlled tools
  ↓
Character Definition
  ↓
Validation
  ↓
Live Preview
  ↓
Human approval
```

The important architectural principle is that the AI would not
manipulate arbitrary Three.js code.

It would operate against the structured Character Definition model
through controlled operations.

This provides a practical small-scale example of a broader enterprise AI
pattern:

> **Convert a manual configuration process into an AI-assisted,
> human-in-the-loop workflow.**

This remains a long-term direction. The immediate priority is to make
the Character Designer itself excellent.

## 🧭 Navigation Profile Thought

The earlier idea of supporting differently sized NPCs remains a
promising future direction.

A future navigation system could distinguish between:

-   Navigation resolution.
-   Unit footprint.

For example:

``` text
40 × 40 world

1 × 1 unit → finer navigation
2 × 2 unit → coarser navigation
```

This could allow small characters to enter spaces that larger entities
cannot while reducing the number of nodes larger units need to evaluate.
