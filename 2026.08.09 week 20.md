# Crack Down Remake --- Weekly Development Summary

## Overview

This week marked another significant architectural step in the project.
The Enemy AI now has a complete, working state-driven behaviour loop,
while the character system has started evolving from a fixed eight-box
model into a reusable, configurable character framework.

The project is increasingly becoming an engine rather than simply a
collection of features.

## 🤖 Enemy AI & FSM

### Full NPC State Machine

Implemented the first complete NPC behavioural loop:

``` text
PATROL
   ↓
CHASE
   ↓
SEARCH
   ↓
PATROL
```

NPC behaviour now works as follows:

-   NPCs begin by following their base waypoints.
-   VisionSystem detects the player.
-   The NPC transitions into `CHASE`.
-   Priority waypoints are generated to pursue the player.
-   Continued visibility can generate additional pursuit paths.
-   When the player is lost, the NPC transitions into `SEARCH`.
-   The NPC pauses and looks around for approximately five seconds.
-   If the player is not rediscovered, a return path is generated.
-   The NPC returns to the appropriate base waypoint.
-   Normal patrol resumes.

### State ownership refactor

The biggest architectural change was moving behavioural responsibility
back into the NPC.

Previously, VisionSystem and WaypointManager were beginning to make
decisions on behalf of the NPC.

They now report information instead:

``` text
VisionSystem ──► NPC ──► FSM ──► Behaviour
WaypointManager ──► NPC
```

VisionSystem reports what it sees. WaypointManager reports path/waypoint
events. The NPC decides what those observations mean and controls state
transitions.

This makes future state additions considerably easier to manage.

## 👁️ VisionSystem

VisionSystem now supports:

-   Distance-based visibility testing.
-   Angle-based field-of-view testing.
-   Initial raycasting for line-of-sight testing.
-   Debug visualisation.
-   Status indicators above NPCs.

The NPC head was also separated into a `HeadGroup` containing the head,
face and FOV representation, allowing the head and its vision cone to
rotate independently of the body.

## 🗺️ Pathfinding & Waypoints

Priority waypoint behaviour is now fully integrated.

NPCs can:

-   Maintain their original base waypoint set.
-   Temporarily receive priority waypoints.
-   Continue receiving new pursuit paths while chasing.
-   Return to their stored base waypoint system after pursuit/search has
    ended.

The WaypointManager has become a reusable path-management component
rather than a source of NPC behavioural decisions.

A new future idea also emerged: navigation profiles for differently
sized units. A larger unit could potentially use a coarser navigation
grid while smaller units retain finer navigation and access to tighter
spaces.

The distinction between **navigation resolution** and **unit footprint**
was identified as an important future design consideration.

## 🧍 Character System

The original eight-box NPC is now being treated as a reusable character
template.

A new defaults/configuration class contains dimensions and proportions,
allowing individual characters to override the standard relationships.

The planned system can also include or exclude individual sub-elements
of the eight-box model.

This should allow very different characters to share the same underlying
animation and behaviour systems, including future Scientist,
maintenance, security and robot characters.

The concept also opens the door to recreating Silent Running-style
robots such as Huey, Dewey and Louie using the same character framework.

## 🎨 Texture & Pixel Art

The Scientist became the first character to receive a substantial
graphical upgrade.

The original texture workflow used tiny textures matching the model's
conceptual unit sizes. The new approach keeps the geometry unchanged
while allowing much higher-resolution textures.

A 400% nearest-neighbour resize was used as the starting point for the
new Scientist textures.

The original textures were copied into `/old` folders so the evolution
of the artwork remains preserved.

### Paint.NET

Paint.NET was introduced as a new pixel-editing tool, particularly
useful for nearest-neighbour resizing and detailed pixel work.

The larger textures provide much more room for:

-   Facial detail.
-   Glasses.
-   Clothing folds.
-   Pockets.
-   Pens.
-   Seams.
-   Shadows.
-   Character-specific visual details.

An interesting technique also emerged: textures can deliberately "cheat"
the limited geometry by painting visual folds and transitions that make
the low-poly model appear more detailed when animated.

The Scientist's textures even use painted portions of the Pockets of
Holding on the leg surfaces to help preserve their appearance during
movement.

## 🛠️ Development Philosophy

A major theme this week has been separation of responsibility.

The project increasingly follows:

``` text
System observes / performs one responsibility
                    ↓
              NPC receives information
                    ↓
              NPC/FSM decides
                    ↓
              Appropriate system acts
```

This architecture is making it possible to add functionality without
allowing individual systems to become responsible for the overall
behaviour of the NPC.

The same philosophy is now appearing in the character system: geometry,
proportions, textures, components and behaviour can evolve
independently.
